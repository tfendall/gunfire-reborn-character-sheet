to your build numbers.

The tracker combines what you own, what the game says is active, and what happened during combat. This explains the journey—and the places where information can be lost.

The key distinction: the Damage tab measures damage events. The Build tab assembles bonus percentages from understood contributions. We do not have one authoritative “final weapon bonus” number that we can simply divide among your items.
01 / The big picture

Two paths through the tracker

01 · READ THE GAME

Inventory + statuses

Which scrolls, gems and ascensions are equipped? Which status instances exist? What values does each status expose?

Periodic snapshots, rather than reading pixels from the status bar.
→
02 · INTERPRET

Resolve + match

Evaluate description formulas, recognize damage metrics, identify their sources, and replace catalogue amounts with fresh live values.

Unknown conditions and conflicting readings stay unresolved.
→
03 · SUMMARIZE

Average + display

Sample the synchronous totals, integrate over 30 combat seconds, and show separate bonus families with contributor details.

This produces the Build tab.
Damage path: damage callback → local-player ownership / source classification → damage ledger → reconciliation with the game’s scoreboard → Damage tab. Hits also tell the bonus window when combat is happening.
Research path: property, status, tooltip and formula hooks → bounded diagnostic queues → JSONL logs. These explain the game’s behavior, but an observed research value does not automatically become a displayed bonus.
02 / Where the information enters

A hook listens. A poll asks.

A Harmony hook runs around a game method when that method is called. A poll periodically reads existing game objects. The Build tab depends heavily on polls; it does not depend on you hovering every status icon.

Observed failure → shared fix

The missing link was the percent sign.

Evaluate.OperateWithParam
expression: (lvl*30%)
inputs: lvl=1, n=0
result: "30%"

Old validator: non-numeric-result

The old renderer accepted plain numbers only. The shared fix preserves a trailing percent sign, so the parser can recognize the metric and value.

Pipeline result: the accepted clause can supply +30% Weapon Damage. The other formula can supply Lucky Shot Chance. This fixes the format; it is not a new Hail-specific arithmetic rule.

The live status knows more than the catalogue.

The observed source mapping is gem 51788. A catalogue entry for an equipped level-2 copy supplies +40%; the fresh status supplies the current aggregate instead.

Current merge behavior

Count the captured value once.

With one or more matching copies, replace their matching catalogue amounts with the single fresh source-level value. Do not add +55% on top of the listed amounts.

With no equipped copy, v0.13.48 can still accept a fresh, explicitly identified status from a known source and label it retained status. This path is tested; it still needs live verification after selling the final copy.

Important: the log showed +55% current status while the recorded combat average was still +25%. A new current value does not rewrite earlier combat.

03B / A larger sample catalogue

27 snapshots. A handful of recurring patterns.

Start with the resolved value, then follow the numbered explanation. Expand a sample to see the exact formula inputs and evaluator output.

Read this as a processing guide, not a claim that all these bonuses reached the UI. Every card contains an actual effect-refresh-result from the local logs. Its explanation applies the current v0.13.48 parser and merge rules. Source matching, freshness and competing states can still prevent a recognized value from reaching the display. Repeated names are distinct historical snapshots, not a measured before/after experiment.

Patterns to look for

  1. Same formula shape: Weapon Fodder and Skill Fodder use a named field divided by 100.
  2. Same inputs, different scaling: Soul Echo and the Serpent affix both use count and amount.
  3. One description, several outcomes: Last Stand and Vindictive Nature contain clauses we treat differently.
  4. A number is not enough: stored damage, CritX, next-shot bonuses and damage taken need different meanings.

Four checks before display

Formula: Can the game evaluate this template with the available inputs?

Metric: Do we know what the result measures?

Attribution: Is there a fresh, unambiguous source-level contribution?

Window: Was the contribution observed during the combat time being averaged?

04 / Try the calculation

A bonus can be active now without owning the whole average.

Illustration: +30% while active

(30% × 6s + 0% × 24s) ÷ 30s = +6%

Average+6%
Uptime20%
Time observed100%

Synthetic teaching example, not a reconstruction of your run. Assumes the inactive intervals are confirmed zero and the whole window is observed.

What the production window actually does

  • Samples bonuses about every 250ms.
  • Counts combat time around weapon and skill hits, with a two-second grace period. Longer idle time pauses the window.
  • Integrates the previous observation forward; a new value is never applied backward.
  • Unknown intervals are excluded from the average and reduce observation coverage. They are not zero.
  • Pauses and sampling gaps over one second are treated as unknown when they overlap combat.
  • Weapon/player/run changes and resets clear the bonus window. Status-learning mappings also reset on scene changes.
Two different kinds of incompleteness: “100% of time observed” can still accompany an asterisk. We may have sampled the known subtotal throughout the window while an owned effect remained unresolved. Coverage is not the fraction of all effects that we understand.

Average

Sum of value × observed duration, divided by observed duration. The headline averages synchronous totals—not contributor averages from mismatched windows.

Peak & uptime

Peak is the largest known sampled bonus. Uptime is known nonzero time divided by known time. Negative bonuses also count as active.

Hit weighting

Support is narrow: Hawkeye Sight uses confirmed weak-point evidence for its known branch. General burning/shock conditions are not yet reliably measured per hit.

05 / Trust boundaries

What makes it onto the screen?

Accepted

  • Reviewed static rules with known inputs.
  • Fresh, resolved status descriptions with recognizable metrics and sufficient source identity.
  • One source-level bonus replacing multiple catalogue copies, explicitly labelled combined.
  • Learned inactive zero after a complete scan confirms the known status is gone and the ownership signature still matches.
  • Fresh retained statuses with explicit known gem/scroll/blessing identity even after inventory ownership disappears.

Still unresolved or separate

  • Competing live readings for the same source and metric.
  • Conditional maxima presented only in an item description.
  • Unverified target conditions, next-shot applicability and unfamiliar formulas.
  • Base damage, additive bonuses and independent multipliers are not indiscriminately added together.
  • Named hero abilities are mapped conservatively. Seasonal Energy Orb is not automatically Crown Prince’s primary skill.
Why a status icon is useful, but not sufficient

We read the game’s status objects and their descriptions; we do not perform image recognition on the HUD. An icon proves the game is presenting a status. It does not, by itself, prove which target or shot received a bonus, whether a counter is the amount, or whether two statuses should stack.

Why Lucky Shot and CritX look different

The Lucky Shot headline is an observed weapon-hit estimate. CritX is a current weapon property. Neither follows exactly the same percentage-total averaging and asterisk logic as the other bonus headlines.

Performance and debug logging

v0.13.48 caches Build contributor data between sampled updates and caps the named-ability text cache at 1,024 entries. Layout and drawing still run in the GUI. build-menu-cache-profile reports contributor-cache rebuild time roughly every five seconds while it rebuilds in an open menu; it is not a complete frame-time measurement.

Research output uses queues and storage limits. The installed debug configuration allows 2,048 MiB per session and 8,192 MiB for the trace directory. Larger storage limits do not prevent queue drops. A complete displayed-bonus-snapshot requires every numbered chunk for that time/player/epoch/weapon.
